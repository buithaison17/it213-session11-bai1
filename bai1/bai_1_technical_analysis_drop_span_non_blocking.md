## 1. TỔNG QUAN & BỐI CẢNH NGHIỆP VỤ

Trong kiến trúc hệ thống tài chính - ngân hàng số **RikkeiPay Assistant**, lưu lượng giao dịch dự kiến đạt hàng chục nghìn request mỗi ngày với yêu cầu cực kỳ khắt khe về tính sẵn sàng (**High Availability - 99.99%**) và độ trễ thấp (**Low Latency SLA < 200ms**).

Khi tích hợp giải pháp **Distributed Tracing** (thông qua OpenTelemetry Bridge và Langfuse Server/OTLP Exporter) để theo dõi các luồng gọi LLM (Spring AI), truy vấn cơ sở dữ liệu và xử lý thanh toán, một bài toán phòng thủ hạ tầng sống còn được đặt ra:

> **"Hạ tầng giám sát (Observability) là hệ thống phụ trợ (Secondary/Sidecar), tuyệt đối không được phép làm gián đoạn hoặc làm sập luồng xử lý giao dịch cốt lõi (Primary Core Banking/Payment Flow)."**

Nếu mạng gặp sự cố (Network Partition), Langfuse Server bị treo, quá tải hoặc ClickHouse bị nghẽn I/O, ứng dụng Spring Boot không được phép bị block luồng hay cạn kiệt bộ nhớ. Tài liệu này phân tích chi tiết cơ chế **Drop Span** và cấu hình **Non-blocking Batch Processor** nhằm bảo vệ hệ thống trước các rủi ro trên.

## 2. KIẾN TRÚC BATCH SPAN PROCESSOR & NGUYÊN LÝ HOẠT ĐỘNG

OpenTelemetry (OTel) cung cấp hai dạng Span Processor chính:
1. **SimpleSpanProcessor (Đồng bộ - Blocking):** Mỗi khi một Span kết thúc (`span.end()`), luồng hiện tại sẽ lập tức gửi dữ liệu qua mạng tới Collector/Exporter.
2. **BatchSpanProcessor (Bất đồng bộ - Non-Blocking):** Khi Span kết thúc, dữ liệu chỉ được đẩy vào một hàng đợi trong bộ nhớ (**In-Memory Queue**). Một background thread định kỳ gom các spans thành từng lô (batch) và đẩy về Langfuse OTLP endpoint.

```
[ HTTP Request / Payment Flow ]
              │
              ▼
   [ Tomcat Worker Thread ] ──( span.start() / span.end() )
              │
              │  (Non-blocking enqueue: Offer)
              ▼
    ┌──────────────────────────────────────────────┐
    │     In-Memory Bounded Queue (RAM RingBuffer) │
    │     [ Span 1 ] [ Span 2 ] [ Span 3 ] ...     │
    └──────────────────────────────────────────────┘
              ▲
              │  (Poll / Batch Drain)
              │
    [ OTel Exporter Background Daemon Thread ]
              │
              ▼  (Async HTTP/gRPC Export)
    ┌──────────────────────────────────────────────┐
    │  Langfuse Server (OTLP HTTP/gRPC Endpoint)   │
    │             (PostgreSQL + ClickHouse)        │
    └──────────────────────────────────────────────┘
```

### So sánh hai cơ chế

| Tiêu chí | SimpleSpanProcessor (Sync) | BatchSpanProcessor (Async) |
| :--- | :--- | :--- |
| **Tác động Latency luồng chính** | Rất cao (cộng dồn Network RTT của Langfuse vào mỗi request) | Gần như bằng 0 (chỉ mất vài nano-giây để enqueue vào RAM) |
| **Khả năng chịu lỗi khi Langfuse chết** | **Gây thảm họa:** Toàn bộ Worker Thread bị block chờ timeout, hệ thống sập | **An toàn:** Luồng chính tiếp tục chạy bình thường, span được xử lý drop ở queue |
| **Hiệu năng mạng (Network Throughput)** | Kém (1 span = 1 HTTP/gRPC call) | Rất cao (Gom hàng trăm span gửi trong 1 payload duy nhất) |

## 3. PHÂN TÍCH KỸ THUẬT: CƠ CHẾ DROP SPAN & VÌ SAO PHẢI NON-BLOCKING

### 3.1. Hiện tượng "Cascading Failure" (Sụp đổ dây chuyền) & Thread Starvation
Giả sử hệ thống xử lý **500 TPS**. Mỗi request sinh ra 3-5 Spans (Controller -> Service -> Spring AI / OpenAI -> DB Transaction).

Nếu Langfuse Server gặp sự cố phản hồi chậm (ví dụ: thời gian phản hồi tăng từ 5ms lên 5000ms):
- **Nếu dùng cơ chế Blocking (chờ queue trống hoặc chờ export):**
  - Số lượng luồng Tomcat (mặc định 200 threads) sẽ bị giữ chặt ở trạng thái `WAITING` hoặc `TIMED_WAITING`.
  - Trong vòng **vài giây**, toàn bộ Connection Pool và Thread Pool của Tomcat bị cạn kiệt (**Thread Starvation**).
  - Khách hàng không thể thực hiện giao dịch thanh toán, cổng API Gateway trả về `504 Gateway Timeout`.
  - **Hậu quả:** Một lỗi từ công cụ giám sát biến thành sự cố ngừng hoạt động toàn hệ thống (System Outage).

### 3.2. Cơ chế Drop Span (Tail-Drop / Non-Blocking Queue Enqueue)
Để triệt tiêu rủi ro trên, `BatchSpanProcessor` triển khai cấu trúc **Bounded Queue** (hàng đợi có kích thước giới hạn) với cơ chế non-blocking:

1. Khi `span.end()` được gọi trên luồng nghiệp vụ:
   - Hệ thống gọi `queue.offer(span)` (thay vì `queue.put(span)` gây block).
2. **Khi Queue chưa đầy:** Span được thêm vào hàng đợi ngay lập tức (độ phức tạp $O(1)$, thời gian micro-giây).
3. **Khi Queue đã đầy (`max-queue-size` đạt ngưỡng tối đa):**
   - Lệnh `offer()` lập tức trả về `false`.
   - Span mới nhất bị **hủy bỏ ngay trong RAM (Drop Span)**.
   - Một biến đếm metric `otel.bsp.dropped.spans` được tăng lên 1 đơn vị.
   - **Luồng xử lý giao dịch thanh toán của khách hàng tiếp tục thực thi trơn tru mà không bị trễ dù chỉ 1 mili-giây.**

```java
// Logic mô phỏng cơ chế phòng thủ Non-blocking trong BatchSpanProcessor:
public void onEnd(ReadableSpan span) {
    if (!this.queue.offer(span)) {
        // Hàng đợi đầy -> Drop span lập tức, bảo vệ luồng nghiệp vụ
        this.droppedSpansCounter.add(1);
    }
}
```

### 3.3. Nguyên lý Đánh đổi (Trade-off Matrix) trong Hệ thống Tài chính

Trong kỹ nghệ phần mềm ngân hàng, nguyên tắc **Graceful Degradation** (Suy giảm chất lượng dịch vụ có kiểm soát) được áp dụng:

$$	ext{System Availability (Giao dịch thành công)} \gg 	ext{Telemetry Completeness (Đầy đủ dữ liệu Trace)}$$

- **Mất mát dữ liệu Tracing:** Đội ngũ DevOps/SRE tạm thời thiếu một số spans trong thời gian hệ thống giám sát nghẽn.
- **Bảo toàn Giao dịch:** Tiền của khách hàng vẫn được chuyển thành công, số dư được cập nhật chính xác, SLA thanh toán được đảm bảo.

## 4. BẢNG THAM SỐ CẤU HÌNH AN TOÀN TRONG `application.yml`

Dưới đây là thiết lập chuẩn kháng nghẽn cho OpenTelemetry BatchSpanProcessor trong Spring Boot khi tích hợp Langfuse:

```yaml
management:
  tracing:
    sampling:
      probability: 1.0 # 100% trace trong môi trường Dev/Staging (Production có thể điều chỉnh 0.1 - 0.5)
  otlp:
    tracing:
      endpoint: "http://localhost:3000/api/public/otel/v1/traces"
      timeout: 2s # Timeout nhanh để ngắt kết nối nếu Langfuse Server bị treo
      headers:
        Authorization: "Basic <base64(pk-lf-xxxx:sk-lf-xxxx)>"
      export:
        batch-size: 512 # Số lượng trace tối đa gom lại gửi 1 lần (max-export-batch-size)
        schedule-delay: 5000ms # Chu kỳ background thread quét gửi dữ liệu (schedule-delay)
        max-queue-size: 2048 # Dung lượng tối đa của hàng đợi trên RAM (max-queue-size)
        max-export-batch-size: 512
```

### Phân tích chi tiết các tham số phòng thủ:

1. **`max-queue-size: 2048`**
   - **Mục đích:** Giới hạn dung lượng RAM tối đa cấp phát cho bộ đệm Trace. Ngăn ngừa lỗi `java.lang.OutOfMemoryError: Java heap space` nếu Exporter không gửi được dữ liệu trong thời gian dài.
   - **Ước tính RAM:** 2048 spans $	imes$ ~2KB/span $pprox$ **4MB RAM** (con số cực kỳ an toàn cho JVM).

2. **`schedule-delay: 5000ms (5 giây)`**
   - **Mục đích:** Giảm tần suất gửi HTTP request tới Langfuse, gom nhiều giao dịch thành một lượt gửi, tối ưu hóa I/O mạng và CPU overhead.

3. **`max-export-batch-size: 512`**
   - **Mục đích:** Đảm bảo mỗi payload gửi đi không quá lớn (tránh tràn buffer của Langfuse/ClickHouse và tránh gói tin HTTP bị quá dung lượng tối đa cho phép).

4. **`export-timeout: 2s (hoặc timeout: 2s)`**
   - **Mục đích:** Khi Langfuse Server bị nghẽn mạng hoặc lock database, luồng Exporter Daemon chỉ chờ tối đa 2 giây trước khi hủy kết nối (fail fast) và chuyển sang xử lý lô tiếp theo, không làm dồn ứ hàng đợi quá lâu.

## 5. GIÁM SÁT & CẢNH BÁO (OBSERVABILITY CHO CHÍNH TELEMETRY)

Cơ chế Drop Span là lớp phòng thủ tự động, nhưng khi có Drop Spans xảy ra, hệ thống cần phát tín hiệu cảnh báo cho đội ngũ SRE.

### Các Metrics cần theo dõi qua Spring Boot Actuator / Prometheus:
- `otel.bsp.dropped.spans`: Số lượng span bị vứt bỏ do hàng đợi đầy.
- `otel.bsp.exported.spans`: Số lượng span gửi thành công tới Langfuse.
- `otel.bsp.queue.size`: Mức độ sử dụng hàng đợi hiện tại theo thời gian thực.

### Quy trình phản ứng sự cố:
```
[ Drop Spans Metric > Ngưỡng Alert ]
                 │
                 ▼
 1. Kiểm tra tài nguyên Langfuse Server (CPU/RAM/ClickHouse Disk I/O)
 2. Kiểm tra kết nối mạng giữa Spring Boot và Langfuse
 3. Tạm thời scale-up cụm Langfuse hoặc hạ tỉ lệ Sampling (`sampling.probability: 0.2`)
```

## 6. KẾT LUẬN

1. **Tính bất khả xâm phạm của Core Flow:** Tracing và Observability sinh ra để phục vụ hệ thống, không được phép trở thành điểm nghẽn (Single Point of Bottleneck) làm giảm tính sẵn sàng của hệ thống ngân hàng.
2. **Cơ chế phòng thủ đa tầng:** 
   - Sử dụng **BatchSpanProcessor** để tách biệt luồng xử lý (Asynchronous decoupling).
   - Thiết lập **Bounded In-Memory Queue** để chặn đứng nguy cơ tràn bộ nhớ (OOM).
   - Áp dụng **Non-blocking Drop Span** để triệt tiêu hiện tượng thắt cổ chai và Thread Starvation.
3. Cấu hình các tham số `max-queue-size`, `schedule-delay`, `max-export-batch-size`, và `export-timeout` là tiêu chuẩn vận hành bắt buộc đối với mọi dự án Microservices / AI Agent trong môi trường Production của RikkeiPay.
